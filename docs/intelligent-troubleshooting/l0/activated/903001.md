## evidence_dql（自动取证 · 4 条）

### ① 确认现象 · 错误日志 `L::`
```dql
L::csdp_wechat_log:(error_code, trace_id, error_msg, occur_time)
   { service = 'csdp-wechat', error_code = '903001' }
   [ {{time_window}} ]   -- 默认：告警时刻前 15min
   LIMIT 50
```
- 作用：确认 903001 真的在发生、拿到 trace_id 供第③条定位。
- `«待核实»`：csdp-wechat 日志在观测云的**数据源名**（这里假设 `csdp_wechat_log`）；`error_code` 是否为**可过滤字段/tag**。

### ② 依赖健康 · Mongo 指标 `M::`
```dql
M::mongodb:(connections_current, connections_available, op_slow_count, uptime)
   { host = '10.6.104.169' }
   [ {{time_window}} : 1m ]
```
- 作用：看连接是否打满、慢查询是否激增、实例是否可达（uptime/有无数据）。
- `«待核实»`：MongoDB 指标的**数据源名与字段名**（取决于观测云 Mongo 集成实际命名，可能是 `mongodb_connections`/`mongodb.connections.current` 等）。

### ③ 定位 · 调用链 `T::`
```dql
T::tracing:(service, resource, duration, status)
   { trace_id = '{{trace_id}}' }
   ORDER BY start_time ASC
```
- 作用：在整条链路里找出 `status = error` 且 `resource` 指向 mongo 的那一跳，把根因钉到 DB。
- `«待核实»`：APM/链路是否已接入、`trace_id` 能否直接查 span。

### ④ 影响面 · 应用错误率 `M::`（可选）
```dql
M::apm_service:(error_rate, request_count)
   { service = 'csdp-wechat' }
   [ {{time_window}} : 1m ]
```

- 作用：量化影响面（错误率升幅），辅助定级与结论话术。

## anomaly_criteria（什么算异常 · 给判读用的标尺）

| 信号 | 来源 | 判据（初稿） | 含义 |
|---|---|---|---|
| `log_hit` | ① | `count(error_code=903001) ≥ 1` | 确认发生（P0 一般 count 很高） |
| `mongo_unreachable` | ② | 窗口内**无指标数据** / uptime 归零 | 实例不可达（**最严重**） |
| `conn_saturated` | ② | `connections_current / (current+available) > 0.9` `«待标定»` | 连接池打满 |
| `slow_spike` | ② | `op_slow_count > 基线 × 3` `«待标定»` | 慢查询激增 |
| `trace_db_fail` | ③ | 存在到 mongo 的 span `status=error`/超时 | 根因定位到 DB 跳 |

### 结论合成规则（给 orchestrator / LLM 的判读指引）
- `mongo_unreachable` 命中 → 根因「**实例不可达**」→ 恢复：联系树朝 + 重启实例（`manual_write`，**人工确认**）。
- `conn_saturated` 命中但可达 → 根因「**连接打满**」→ 同上，并提示排查连接泄漏。
- 仅 `log_hit`、但 ② 指标正常 → 可能**非 DB 本身**（如网络/客户端）→ **降置信度 + 转人工深查**，不硬下 DB 结论。

> 呼应信任工程五约束：每条 `is_anomaly` 判断都绑定上表某个信号的证据；恢复动作全部来自 KB、写操作 `requires_approval`；证据不足时 abstain（走最后一行）。
