IT 智能排障系统
架构与演进蓝图

把故障处理从「人工翻系统 + 经验判断」升级为「告警驱动 · 智能路由 · 自动取证 · 人机协同诊断 · 知识闭环」。本文沉淀前期讨论共识，作为团队对齐、立项与分工的基线。

范围 CSDP 工单/客服链路（首个域） 证据源 观测云 Guance · DQL 状态 架构已收敛 · 主流程演练已跑通 · v0.3
01
背景与目标

为什么做，以及做成什么样

IT 系统组件相互依赖，排障已从单点定位变成跨系统、跨团队、跨数据源的综合诊断。当前高度依赖人工经验，在故障高峰、经验不均、链路复杂时容易响应慢、路径散、结论不一致、SLA 达不成。

五个核心痛点
  1. 排障入口分散——告警、日志、监控、变更各在一处，缺统一上下文视图
  2. 经验依赖严重——新人难判断「先查什么、怎么查、什么算异常」
  3. SOP 难执行——多为静态文档，不能按告警自动匹配、取证、校验
  4. 跨团队协同成本高——群里反复追问，缺结构化流转
  5. 过程难沉淀——根因与判据处理完即散失，同类问题重复排查
三个预期效果
  • 1
    提升响应效率——按告警内容/服务/错误码自动匹配场景与 SOP，给出推荐路径。
  • 2
    缩短 MTTR——自动聚合日志、指标、变更、依赖状态等证据，减少无效排查与跨团队等待。
  • 3
    降低一线门槛——专家经验固化为可执行 SOP，一线即可完成初诊、取证与分流。
关键前提已具备。 团队已有一份结构化的《故障与措施》知识库（服务 → 模块 → 功能 → 场景 → 错误码 → 恢复方案 → 问题定位 → 结构化日志），并含错误码体系与告警级别枚举。这让「专家经验固化」这一最难环节已完成大半——项目起点接近 L0.5。
02
核心设计原则

确定性优先，LLM 兜底：双路脊柱

系统能不能上生产，取决于一条边界：能确定的事交给查表与工具，模糊/未知的事才交给 LLM。 这条边界划在「错误码是否命中」上——已决策锁定。

告警 / 工单 / 手动 · 提取 system · error_code
↓
(system, error_code) 命中 SOP 库？
命中 · 确定性主干
  1. 查表拿到 SOP（原因 / 恢复方案 / 责任团队）
  2. 按 evidence_dql 模板执行取证
  3. LLM 仅做「判是否异常 + 合成人话结论」
→ 零幻觉 · 可审计 · 快
未命中 · 未知异常分支
  1. LLM 分诊，动态构造 DQL 取证
  2. 人机协同定位，给出候选结论
  3. 处理完 → Skill Evolver 沉淀为新条目
→ 学习入口 · 越用越全

取证也确定性化

「问题定位」列落成每个错误码绑定的 DQL 模板，取证不靠 LLM 猜。

恢复动作三分级

action_type 区分 auto_readonly（自动）/ human_contact（找对人）/ manual_write（写操作，人工确认）。度量看「可自动化率」，不拿覆盖率冒充。

API-first

核心只产出结构化「诊断结论对象」，IM 卡片与 Web 台都是它的视图。

不训权重

一/二期不碰 RL/GRPO 权重训练——只用 Skills 注入、Memory、Skill Evolver 三样非训练能力。

05
取证方案

观测云 · 一个 DQL API 覆盖多源证据

观测云连接器本质是「执行一条 DQL 查询」。DQL 的命名空间正好覆盖排障所需的全部证据类型——换命名空间即换证据源，让「跨源关联」几乎零额外接入成本。

命名空间证据类型SOP 中的用途
L::日志按 trace_id / error_code / service 拉结构化日志，确认现象
M::指标错误率、连接数、慢查询、磁盘 / 内存（MongoDB 类故障必需）
T::链路 APM按 trace_id 追调用链，定位是哪一跳失败
D::拨测外部可用性探测
R:: / E::RUM / 事件前端影响面、发布 / 变更事件

示例：错误码 903001（数据库访问异常）绑定的取证模板

# evidence_dql —— 与 error_code 绑定，取证确定性执行
L::csdp_log:(error_code, trace_id, error_msg, occur_time)
   { service=?, error_code='903001' } [time_window]

M::mongodb:(connections, slow_queries, disk_used)
   { host='10.6.104.169' } [time_window]

# LLM 只负责：对照 anomaly_criteria 判断是否异常，合成结论
# recovery_steps → 联系 DBA 重启实例 / 参考 Mongo 恢复方案（requires_approval）
部署约束。 观测云端点为内网地址（*.prd.sangfor.com），当前云端环境不可达。连接器与整个排障运行时最终须部署在能访问内网的环境；开发期可用录制响应打通逻辑，真实联调在内网进行。DF-API-KEY 作为运行时密钥配置，不写入 SOP 正文或 prompt。

证据源开放适配（D8 · 多平台 Observability Abstraction Layer）

观测云是首个适配器，不是唯一。 证据源必须开放、可插拔——后续可接 Zabbix / Prometheus / 日志平台。关键是把三件事拆开：要观测什么（进 SOP，平台无关）/ 在平台 P 上怎么查（绑定注册表，每平台一份）/ P 的响应怎么归一（适配器）。

# SOP 存平台无关「意图」，不含任何平台查询语法
EvidenceRequest{ signal_kind:"metric", target:{host, metric:"mongo.connections"}, required:true }
        │  Router：按 (system, signal_kind) 选平台适配器（主+备）
        ▼
Adapter(guance|zabbix|prometheus|recorded|fixture) → 造查询 · 执行 · 归一
        ▼
EvidenceResult{ observed:{connections_current, ...} }  # 规则引擎跑在归一字段上，平台无关

D-A · 绑定放注册表

SOP 只存意图；`(signal, 平台)` 查询模板放绑定注册表——加平台不改 SOP。

D-B · 按 system+signal 路由

一个系统可多平台混用：日志走 Loki、指标走 Zabbix、链路走观测云。

D-C · 归一化词汇表

各适配器归一到同名 canonical 字段——同一条 anomaly_criteria 跨平台零改动成立。

加 Zabbix = 加一个绑定 + 一个 adapter，零改 SOP、零改 anomaly_criteria、零改回归集。契约草案（EvidenceRequest / SourceAdapter / 归一词汇表 / 路由配置）详见 observability-abstraction-design.md。

07
演进方式

能力成熟度阶梯 L0 → L5

按 竖切 → 加源 → 加智能 → 加闭环 推进，每级独立交付价值并为下一级降风险。原则：先打通一个错误码的完整竖线，再横向复制——每个 error_code 就是一个可独立上线的小闭环。

级别能力交付价值依赖MetaClaw
L0知识底座——xlsx → 结构化 SOP 库（error_code 可查）静态查询已快过翻文档无（现可做）—
L1单点取证——单错误码竖切，观测云按 trace_id 拉日志确认验证地基，单场景自动取证观测云 API—
L2端到端诊断——告警驱动 + 编排 SKILL，自动路由/取证/出结论响应效率兑现L1 + 编排层Skills
L3跨源关联——日志+指标+链路+发布变更；跨团队结构化流转MTTR 大幅缩短多命名空间Skills
L4人机协同+闭环——写操作人工确认；未知异常→候选→晋升降低门槛，知识不靠人L3 + 记忆Memory · Evolver
L5自进化——相似历史召回、SOP 命中率自优化、路由自学习越用越准，去个人依赖数据积累元学习

「未知异常」是天然闭环入口

《故障与措施》已列该分类（全局中间件捕获、未登记）。命中走确定性 SOP，落到未知即触发 MetaClaw 学习——接口已埋好。

协同层价值别排最后

最痛的是「群里反复追问」。L3 的结构化流转——转 DBA 时自动带齐 trace_id/日志/已确认现象——是一线感知最强的价值点，值得在 L3 优先。

08
部门级复用 · 平台化

从单系统打样到多系统平台：横轴

前面的 L0→L5 是单系统能力深度；多系统接入是另一根轴——接入广度。策略是先走深、再铺宽，而非一上来做通用平台。

纵轴 · 能力深度

L0 → L5，把一个系统（CSDP）从知识底座打到自进化，验证闭环。

横轴 · 接入广度

从打样中抽出可复用平台能力，再横向低成本复制到部门内各系统。

下列带 承重墙 的，需在 CSDP 打样阶段就预留接口，避免第二个系统接入时推翻重来；其余可等第 2–3 个系统再补。

① 分层接入 —— 低摩擦与强自动化并存

不强求所有系统先统一标准，按 错误码粒度 成熟：一个系统可以"部分标准"，高频码先走确定性，长尾继续 LLM。

接入档系统需提供得到的能力
轻接入仅告警（无结构化错误码）走 LLM 诊断路，给推荐方向 + 通用中间件排查（≈每系统从 L1 起步）
标准接入结构化错误码 + trace_id + evidence_dql确定性主干：自动取证、命中即答（L2+）

② 复合路由键 —— 一条回退链 承重墙

路由键从平面 error_code 升级为分层解析，让"确定性优先、LLM 兜底"在多系统下依然成立。

1
业务层精确命中 (system, error_code)

拿业务 SOP；若 type=依赖异常且 cause 指向中间件 → 同时挂载公共层 SOP（委托取证与恢复）。

2
公共层类型匹配 (infra_type, signature)

业务层未命中，但错误可归类为基础设施（Redis/Mongo/MQ/网络）→ 查共享的公共层。

3
LLM 诊断兜底

都没有（轻接入 / 无结构化码）→ LLM 动态取证诊断 → 生成候选条目回流知识库。

③ 公共 / 业务两层知识库 承重墙

公共层 · 全部门共享

key = (infra_type, signature) · 平台团队维护
  • infra_type redis/mongo/mq/k8s/网关/网络
  • signature · evidence_dql[]
  • recovery_steps[]
  • owner_team 中间件/平台
  • ← 你们表里"参考中间件XX恢复方案"即此层

业务层 · 每系统一套

key = (system, error_code) · 各团队维护
  • system · error_code
  • cause · type
  • delegates_to → 公共层条目
  • recovery_steps[] 仅业务特有部分
  • owner_team · visibility · version
委托去重 ↺  业务层 type=依赖异常 的条目不重写"怎么重启 Mongo"，只记"是 DB 问题"并委托公共层。CSDP 903001、B 系统 DB 错误、C 系统 DB 错误共用同一份公共层条目——N 个系统的中间件故障不再是 N 份重复 SOP。

编排层 · 信任工程

③层怎么落：自建 orchestrator + MetaClaw

这一节回答"故障上下文进来后，那个'大脑'到底怎么一步步跑、怎么防止 LLM 乱下结论"。基于 MetaClaw 代理层实际实现（api_server.py 的 skill 注入是单轮拼进 system prompt、工具调用在客户端执行）得出的结论。

MetaClaw 的边界

MetaClaw 每轮注入对的方法论 skill + 记忆，会话后沉淀经验——但它不跑多步循环、不执行工具。跑循环、调 DQL、做输出校验是另一个宿主的事。

③编排层 = 两半

自建轻量 orchestrator

跑循环 · 调 MCP 工具 · 输出校验
  • 确认→取证→关联→结论 的多步循环
  • 调 MCP 工具 SOP 查询 / 观测云 DQL
  • 校验闸门 证据/置信度/审批标记
  • 严格管控：确定性优先、写操作审批

MetaClaw 代理

orchestrator 的每次 LLM 调用都经它
  • Skills 注入 按场景注入排障方法论
  • Memory 召回相似历史故障
  • Skill Evolver 未知异常经验沉淀为新 skill
  • 拿到学习能力，不牺牲管控

三角色 · 一次 LLM 调用怎么穿过 MetaClaw

orchestrator 是「死」的程序（照章、可控），LLM 只在需要判断时被叫，MetaClaw 夹在两者之间让每次调用自动带上经验、事后学习。

思考

一次故障里，大部分步骤走 ①（orchestrator 直接调 MCP，纯查表/取证/校验，可控可审计）；只有「需要判断」那一步走 ②——而这一步穿过 MetaClaw，顺手拿到方法与记忆、事后沉淀。「让 LLM 调用走 MetaClaw」在工程上就是：把大模型的 API 地址指向 MetaClaw，仅一行配置。

两层 SOP —— 结构化 KB 与 MetaClaw skill 各管一段

这也钉死了"SOP 到底存哪"：确定性数据走 KB（工具查、凭证不入模型），方法论走 MetaClaw skill（注入 prompt）。

控制流

IncidentContext
  ├─[命中] SOP查询工具(system,error_code) → evidence_dql[] + 恢复步骤 + anomaly_criteria
  │        └ orchestrator 逐条跑 DQL(MCP) → 证据

  └─[未命中] LLM 分诊: 白名单内动态构造 DQL → 取证 → 低置信结论 + 强制人工确认

LLM 信任工程 · 五条硬约束

MetaClaw 不强制结构化输出，所以信任工程在 orchestrator + 工具契约层做——把 LLM 能"发挥"的面压到最小。

1 · 确定性优先

LLM 从不生成恢复动作；命中时恢复步骤直接来自 KB，LLM 只做证据判读 + 话术合成。

2 · 强制引用证据

每个 is_anomaly 判断必须绑定一条 evidence(dql+result)，无证据不许下判断。

3 · 结构化输出 + 校验闸门

必须产出强 schema 的 Diagnosis，过校验：证据齐？置信度符？写操作都标 requires_approval？

4 · 置信度校准 + abstain

证据不足/矛盾 → 强制低置信 + 建议人工取证；宁可说查不准也不编，低置信不触发自动建议。

5 · 上下文预算

只把命中的方法论 skill + 本 incident 证据进 prompt，不灌整个 KB（用 MetaClaw top_k 检索控制）。

为什么不直接上 ReAct —— workflow 与 agent 分层用

我们的 orchestrator 是 code-planned workflow（代码写死流程），不是 LLM 每步自主决定的 ReAct agent。区别在"谁开车"。

ReAct（LLM 自主）我们的编排（code-planned）
谁决定下一步LLM 每步决定、自选工具代码写死流程
执行路径每次可能不同固定 · 可复现 · 可审计
延迟 / 成本多轮往返，慢而贵少数几步，快而省
适合未知 · 需灵活探索已知套路 · 要可控

不是二选一，而是按双路脊柱分层用：

命中 · 已知
  1. code-planned workflow——固定流程
  2. 可控、可审计、快；套路已知不需自主
未命中 · 未知
  1. 放出 ReAct 式 agent 自主探索
  2. 套笼子：DQL 白名单 + 结论强制低置信 + 人工确认
呼应 Anthropic《Building Effective Agents》的判断：能用 workflow 就别上 agent，只在真需要灵活性时才用 agent。我们即：已知走 workflow，未知才放 agent 出来。

框架选型（骨架，不改架构）

LangGraph 推荐

状态图 + 条件边 + human-in-the-loop 中断/checkpoint——天然对上"固定流程 + 命中/未命中分支 + 写操作审批闸门"。未命中节点可内嵌 ReAct 子 agent。

Pydantic AI

强项是结构化输出 + 校验，正好对上"强 schema Diagnosis + 校验闸门"。更轻。

原生 SDK 自写

命中路流程很短，用 tool-use + 一段自己的状态机也够——最轻、最可控。

三条硬约束（否则架构就破）：① LLM 的 base_url 能指向 MetaClaw（OpenAI 兼容），才吃得到注入/记忆/沉淀；② 支持结构化输出 + 校验；③ 支持 human-in-the-loop 审批 + 工具走 MCP。框架只是 orchestrator 的骨架——LLM 调用照样穿 MetaClaw、工具照样 MCP、信任五约束照样在校验层，用框架是省搭建、不是换设计。

上线取信 · 放权阶梯

怎么敢用、怎么让领导放心逐步放权

知识只有 ~20% 可执行，系统必然会错——不能直接开。核心思路：不追求知识全好才上线，而是"先证明、再按挣到的信任逐格放权"。这套策略正是管理主要矛盾（知识质量）的办法。

两个互补机制

历史回归集（离线）影子模式（在线）
时机上线前 + 每次改动后上线后、真实流量上
怎么做过去已解决故障回放，对比结论 vs 真实根因与真人并行跑实时告警，输出先不给一线、只记录比对
作用准确率基线 + 回归闸门（改动不许把分改低）抓离线测不到的：新模式、数据漂移、真实命中率
Ground truth已知真实根因（《故障与措施》表 + 历史工单）人实际处置结果 + 专家定期抽检

回归集起步不用多：每个试点错误码挑 20–30 条真实历史故障即可。

放权阶梯 —— 按错误码粒度逐格毕业

放权不是一刀切开关，而是一级一级挣，每级由上一级指标达标解锁；且按错误码/场景粒度——某个错误码证明了才升档，别的仍在低档。（门槛数值留空，待真实数据标定。）

档系统做什么人做什么风险解锁条件
S0 影子全程跑，输出隐藏，只记录比对照常人工排障零起点
S1 建议输出作为建议展示（copilot）决定一切，可采纳/否决极低影子期根因正确率 ≥ 阈值
S2 只读自动取证自动跑只读取证，给证据+结论判读、决策、执行低（只读）采纳率达标 且有害错误≈0
S3 半自动高置信+高命中码：自动只读动作/自动分派管写操作与兜底中该码 S2 准确率达标
写操作永不自动永远人工确认——

什么算「对」—— 评判标准

根因 / 路径正确率

根因判定是否等于实际根因；推荐路径是否命中真正有效的动作。

误报 / 漏报

把正常判成异常、或异常判成正常，分开统计。

⚠ 置信度校准

最危险的是高置信却错——单独盯死；高置信错误零容忍。

有害错误零容忍

把人引向错方向（有害）零容忍；只是没帮上忙（无害）可接受。两者分开看。

给领导的定心丸

"只在被证明可靠的错误码上自动跑，其余全程人工监督；覆盖面随知识补全逐格扩大，且写操作永远要人点头。"——不需要知识全好才敢上线。这也是 实践认识论：方案是假设 → 影子/回归是实践检验 → 修正认知 → 再放权。

放权期间的护栏

  • 一键回退纯人工（kill switch），随时可停。
  • 爆炸半径限制：按系统/级别限流；P0 一开始就跑影子（越早攒准确率越好）但绝不自动。
  • 否决即触发复审：人每否决/纠正一次 → 记录 → 自动标记该 SOP 复审（喂闭环）。

知识运营机制

那 80% 空缺谁来补、怎么不饿死

知识库的天花板 = 系统的天花板（主要矛盾 · 可执行 SOP 仅 ~20%）。R6 最难的不是技术，是"一线凭什么花时间补 SOP"——静态排障文档就死在这。所以核心不是"再找人写文档"。

核心原则：让沉淀「顺手」，而非「额外负担」

嵌进处置流程

关闭时系统已把本次证据/动作/结论预填成候选条目，人只需确认/微调——把"写文档"变成"点确认"。

贡献者自己受益

补了这条 SOP，下次同类故障自己就省事（甚至升自动档）——从"成本"变"给自己减负"。

专家只审核 + 兜底

专家做审核/疑难兜底/定标，不当文档工——经验通过"审核关"沉淀。

本质是群众路线：从一线处置中来（沉淀）→ 补全后回流去帮一线（复用）。

知识三来源

来源是什么靠什么机制
存量挖掘《故障与措施》表 + 历史工单 + 群聊 + 静态文档，一次性挖成结构化条目起步地基（人工 + LLM 抽取）
增量沉淀每次处置完（尤其未知异常 / 影子比对）→ 自动生成候选条目Skill Evolver + candidate→promotion
主动补全 backlog度量指出"哪些高频码还没 SOP / anomaly_criteria" → 排优先级补数据驱动的补全队列

谁补、谁审、怎么激励

  • 补：处置人顺手点确认（增量）；平台团队按 backlog 主动补（存量 + 高频）。
  • 审：分层归属——业务层由该系统 owner 团队审，公共层由平台/中间件团队审。
  • 激励（没有它会饿死）：贡献看板（谁沉淀了多少有效条目、命中率）→ 进绩效；领导侧把「覆盖率 / 可自动化率」当团队 KPI 倒逼补全。

生命周期 + 质量反馈（SOP 会过期、会变坏）

candidate 候选 → approved 生效 → deprecated 废弃  （带 version）
质量反馈闭环：SOP 用后结果回流——"最近 N 次没解决" / "被否决纠正" → 自动标记复审/降级（trust 章节"否决即触发复审"就是入口）。过期治理：凭证型步骤标为运行时引用；高频 SOP 定期复审。

驱动运营的度量

覆盖率 · 可自动化率 · 命中率 · 采纳率 · 沉淀速度（新增/周）· 过期率 · 复审 backlog——既排补全优先级，也是激励与向上汇报依据。

持久战 · 实事求是

补齐 80% 是持久战，不可能一步到位。现实路径：高频优先、逐步收敛，和放权阶梯咬合——高频码先补先毕业。别对领导承诺"上线即全自动"，要承诺"一台越用越强、覆盖逐格扩大的机器"。

决策记录

已锁定的八个架构决定

✓

D1 · 确定性 / 智能边界 = 「错误码是否命中」

命中走纯查表 + DQL 模板取证（零幻觉、可审计）；未命中才上 LLM。

下游约束 取证也划到确定性侧；LLM 战场只剩未知异常、跨证据关联、结论合成三处。
✓

D2 · 知识库可演进

非静态死表——支持未知异常处理后「候选 → 审核 → 晋升入库」增量成长。

下游约束 schema 自 L0 起带 origin / status；复用 MetaClaw memory 的 candidate/promotion 机制，不另造。
✓

D3 · 中长期收敛到「故障上下文 Web 台」

IM 机器人起步（贴现状、快），中长期统一到含时间线与证据看板的 Web 台。

下游约束 强制 API-first：核心只产出「诊断结论对象」，IM 与 Web 均为其视图；IM→Web 是加视图不是重做。
✓

D4 · 编排 = 自建 orchestrator（LLM 走 MetaClaw）+ 工具走 MCP

自建轻量 orchestrator 跑循环与输出校验；每次 LLM 调用经 MetaClaw 拿 skill 注入/记忆/沉淀；观测云连接器与 SOP 查询各做成 MCP server。

下游约束 MetaClaw 只注入方法+学习、不跑循环；SOP 分两层（结构化 KB + MetaClaw skill）；信任工程五条约束落在 orchestrator + 工具契约层（详见 §10）。
✓

D5 · 上线取信 = 影子 + 历史回归集 + 放权阶梯

放权阶梯 S0 影子 → S1 建议 → S2 只读自动取证 → S3 半自动，写操作永不自动；按错误码粒度逐格毕业；门槛留空待真实数据标定。

下游约束 有害错误 / 高置信却错零容忍；P0 一开始就跑影子但不自动；否决即触发 SOP 复审；每个错误码带「自主档」状态（详见 §11）。
✓

D6 · 知识运营 = 沉淀嵌进流程 + 贡献者受益 + 专家只审核

补全嵌进处置流程（沉淀即点确认）；三来源（存量挖掘 / 增量沉淀 / 主动补全 backlog）；生命周期 candidate→approved→deprecated + version；否决/连续失败触发复审。

下游约束 分层审核归属；覆盖率/可自动化率进团队 KPI + 贡献看板；高频优先的持久战，不承诺一步到位（详见 §12）。
✓

D7 · MetaClaw 集成 = 产品入口一体、领域 Module 与运行时分开

同仓、同发行包、统一启动；排障先保持独立进程与 loopback，通过 ReasoningGateway / KnowledgePublisher Adapter 复用 MetaClaw，不继承或侵入核心内核。

下游约束 Core 不导入排障领域模型；排障只依赖稳定 HTTP 契约。P2 已完成 SQLite 持久化、schema migration、事务 Outbox、静态资源打包与重启恢复；可信身份 / RBAC、真实 Adapter 和统一 Launcher 完成前，仍保持 loopback 独立进程，不并入 Core FastAPI。实施合同见 MetaClaw 集成设计。
✓

D8 · 证据源开放适配（Observability Abstraction Layer）

证据源可插拔多平台——观测云是首个适配器，Zabbix / Prometheus / 日志平台可后续接入。SOP 存平台无关意图（EvidenceRequest），绑定放注册表(D-A)，按 system+signal 路由(D-B)，各适配器归一到 canonical observed 字段(D-C)。

下游约束 加平台 = 加一个绑定 + 一个 adapter，零改 SOP / anomaly_criteria / 回归集；`EvidenceQuery.query`(DQL 串) 需重构为 EvidenceRequest + SourceAdapter/Router（复核缺口 G7）。契约见 证据源开放适配设计。

风险与修正

用「实事求是」复核后的诚实修正

评审方法：调查研究 → 矛盾分析 → 批评与自我批评 · 数据取自《故障与措施》原表

架构骨架成立（双路脊柱、error_code 确定性键、两层知识库、API-first 均予保留）。但一次基于真实数据的复核暴露出一个诚实落差：蓝图描绘的自动化程度，超出了现有知识资产能支撑的程度。

结构性问题 R1 / R3 / R5 已落进正文各节；R6 已立知识运营机制（§12）；R2 / R4（anomaly_criteria 补全、审核 SLA）属知识与运营侧，随 L0 补全推进。

主要矛盾

系统的「自动化诊断能力」 ↔ 现有 SOP 知识的「结构化与可执行程度」——而矛盾的主要方面在知识侧，不在技术侧。系统天花板不由架构或 MetaClaw 决定，而由知识库里「错误码→可机器执行的取证与恢复」的高质量条目有多少决定。
